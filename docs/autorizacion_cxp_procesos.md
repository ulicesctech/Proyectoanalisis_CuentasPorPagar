# Capacidades de procesos de pago CXP

La consulta de identidad une `USUARIO.USU_ID_ROL` con `ROL.ROL_ID_ROL`. El servidor
compara `ROL_NOMBRE_ROL` en mayúsculas y sin espacios; solo concede una capacidad
cuando usuario y rol están activos y el nombre normalizado corresponde a un único
registro de `ROL` (incluidos los roles inactivos al comprobar duplicados).

| ROL_NOMBRE_ROL | Capacidad | Acciones del proceso |
| --- | --- | --- |
| `OPERADOR_CXP` | `CREAR` | Crear y solicitar un pago |
| `APROBADOR_CXP` | `APROBAR` | Aprobar o rechazar una posición |
| `TESORERIA_CXP` | `TESORERIA` | Programar, emitir, entregar, confirmar y reimprimir |
| `SUPERVISOR_CXP` | `ANULAR` | Anular |

Los IDs numéricos siguen siendo las PK/FK de Oracle; no hay IDs predeterminados
en el servidor. El esquema disponible tiene un solo `USU_ID_ROL` por usuario,
pero muchos usuarios pueden apuntar al mismo rol. Un rol desconocido o inactivo
no concede capacidades. Si el nombre de uno de los cuatro roles es ambiguo al
ignorar espacios y mayúsculas, la identidad produce un error de configuración.

Las reglas de aprobación de pago y lote por monto, nivel y demás condiciones
siguen aplicándose al solicitar y decidir. La capacidad `APROBAR` no las sustituye:
para aprobar o rechazar una posición, `USUARIO.USU_ID_ROL` también debe coincidir
con `CXP_APROBACION.ID_ROL_APROBADOR`, fijado desde la regla aplicable. Con la
matriz actual, las reglas `PAGO` y `LOTE` que deban poder decidirse con
`APROBADOR_CXP` deben apuntar al ID real de ese rol. Revisar las reglas existentes
en el diagnóstico; no se cambian automáticamente. El flujo conserva la
prohibición de decidir dos posiciones de un mismo proceso.
Entre usuarios de `TESORERIA_CXP`, el programador, el ejecutor y quien confirma
deben ser tres personas distintas; se comparan sus IDs de usuario, no sus roles.

## Preparación de Oracle

1. Ejecutar **solo** los SELECT de `database/oracle/09_migraciones/diagnostico_roles_proceso.sql`
   y confirmar columnas, generador de `ROL_ID_ROL`, nombres existentes y asignaciones.
2. El `DDL_CORREGIDO_F5.sql` indicado para este proyecto define `ROL_ID_ROL`
   como `GENERATED BY DEFAULT ON NULL AS IDENTITY`. Revisar
   `preparar_roles_proceso.sql`, que usa esa estructura, y verificar con el
   diagnóstico que la base destino coincide. Si la
   instalación usa una secuencia u otro generador, usar la plantilla alternativa
   `preparar_roles_proceso_ids.sql` con IDs obtenidos de ese generador confirmado.
   Ninguna plantilla renombra o activa roles compartidos.
3. Crear los usuarios por el mecanismo de administración de `USUARIO`. Para cada
   usuario nuevo sin rol, la plantilla independiente
   `preparar_asignacion_usuario_rol_proceso.sql` permite elegir **una** asociación
   por nombre. No modifica usuarios que ya tengan `USU_ID_ROL`.
4. Contar con al menos tres personas activas de `TESORERIA_CXP` para probar el
   flujo completo de programar, ejecutar y confirmar un mismo pago. Las otras
   capacidades requieren usuarios con sus respectivos roles. Ningún script se
   ejecuta desde el código ni se incluye en el instalador de migraciones.

## Sustitución de la identidad provisional

Hoy `resolverActor` toma `X-CXP-Actor-Id`, consulta el usuario activo y pone el
resultado en `res.locals.cxpActor`. El selector «Operando como» permite elegir
ese ID; no demuestra la identidad de la persona.

Cuando exista login, el middleware de sesión deberá obtener el ID de `USUARIO`
del sujeto autenticado en el servidor, consultar nuevamente usuario y rol activos
y llamar a `actorDesdeUsuario`. Mantendrá `res.locals.cxpActor` y los controles
de autoría/segregación, pero ignorará el encabezado suministrado por el cliente.
El cliente deberá mostrar el usuario de la sesión en lugar del selector, dejar
de enviar `X-CXP-Actor-Id` y ocultar el listado provisional de usuarios. Las
capacidades continuarán derivándose del rol consultado en Oracle en cada petición.
